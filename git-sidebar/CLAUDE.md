# git-sidebar

Spec: `docs/specs/git-sidebar.md` (R*n*). Investigation: `docs/investigations/git-sidebar.md` (INV §*n*, P*n*; the host facts the diff relies on, H*n*, are INV §13.7).

## Structure

- `git_sidebar.ts` only wires the editor to `lib/`. `makeSection` holds one window's section, with all of its state; the module around it routes events to sections and owns what is the editor's alone (the timer, the menu, the keyboard's region, the palette). The `lib/` modules never touch editor globals: git runs through the injected `Runner` and time comes in as arguments. Put logic in `lib/` and unit-test it there.
- `tests/fake_editor.ts` fakes the part of Fresh's `EditorAPI` the plugin uses. It installs `getEditor`, `registerHandler` and a manual `Date.now`, and `advance(ms)` fires timers, delays and process completions in order. A newly used editor API has to be added there.
- `tests/plugin.test.ts` re-imports the entry with `?load=N` for each test, so every test gets fresh module state.
- `tests/fixtures/` holds real git outputs: `*.z` `git status` (the parser), `log-*.z`, `difftree-*.z` and `show-*.txt` (the Graph), and `remote-*.txt` pull and push outcomes (`rc`, stdout, stderr) against local bare remotes. To change or add one, edit `tests/fixtures/record.sh` and re-run it; don't hand-edit the files. `record.sh` runs the plugin's own argv, and `history.test.ts` and `remote.test.ts` check that it does.
- `tests/live/fixture.sh <name> [--devcontainer <image> | --volume]` builds the acceptance repository under `~/.cache/gs-live/` for checks in a running editor; the names `graph` (A30's history, a bare `origin` and a second clone `graph-2`) and `graph-long` (120 commits) build the Graph's.
- **No import cycles, type imports included.** Fresh 0.5.9 bundles each module into a function run once, in dependency order, that destructures its imports when it runs; it counts `import type` and `export … from` as dependencies, and a cycle fails at load with `ReferenceError: __mod_<name> is not initialized`. Node and `fresh --check-plugin` miss it; `tests/imports.test.ts` catches it. That is why `lib/graph_keys.ts` exists and why `badName`, `dirReason` and `nameReason` live in `status.ts`.

## Invariants the host forces

- **Section lifecycle (INV §5, P2, §11).**
  - One section per window (R28), each with its own panel id from `panelIdFor(windowKey(stable_id, root))`: a panel id is the plugin's, editor-wide, and the saved collapsed state is keyed by it. Never derive it from the window id (new on every launch) or the root alone (two windows can share one).
  - Mount synchronously once a `.git` is found: at load for the active window, and for any other in the first `active_window_changed`, or the first `active_buffer_changed` of a window with no section (the first focus announcement comes without a switch, INV §11.3). Never before the window is first shown, or its saved layout is lost (INV §11.2).
  - Never unmount to refresh: that loses the collapsed state and height. Update in place. Row buttons are part of the signature, so a button appearing is an in-place update too.
  - A title change (such as a branch switch) forces a remount. Every mount must pass `closable: false`, `startBlurred: true` and `scope: { window }`, because a mount without them reverts to a closable section that takes focus.
- **Expansion and selection.** The plugin owns them by item key. A remount resets the host's copy, and the host keeps the selection by index, so the plugin re-pushes both. An update in place ignores the spec's seeds, so a change the plugin makes to `expanded` itself (Enter's toggle, `prune`) is pushed too.
- **Stale runs.** Every awaited git or docker run re-checks `epoch`, which changes on authority change, trust change and end. A new async step must check it too.
- **Where git runs (INV §7).** In a dev container the filesystem stays on the host. With a bind-mounted workspace, git runs on the host through `spawnHostProcess`, which returns `exit_code`, not `code`. `runOnTarget` in a container gets the host cwd and its `kill()` does nothing. A volume workspace runs no git and shows a notice instead.
- **No `index.lock` from refreshing.** Status, the diff's `cat-file` reads, and the Graph's and Pull/Push's reads (log, diff-tree, show, for-each-ref, remote, config, symbolic-ref) run with `--no-optional-locks` (R11); rev-parse takes no lock. Only a stage, unstage, commit, pull or push the user asked for writes to the repository, and it runs outside the scheduler, through `OpQueue`, one at a time: commits, pulls and pushes queue with stages and unstages, in the order asked (R26, R36).
  - Pull and push run as `env <assignments> git pull|push …` through `runWrite(…, "env")`, never killed: a killed push still lands, and a killed pull leaves its fetch running (INV §8 P37 g, h). The assignments (`remoteEnv`) turn every credential and ssh prompt into a fast failure, since Fresh gives git no input but git and ssh can draw on the editor's terminal (P37 a, P39 a, d). They also set `LC_ALL=C`, because `classifyPull`/`classifyPush` match git's English text and a gettext build translates it; hooks git runs for a pull or push inherit `LC_ALL=C` too. `record.sh` records the remote outcomes with the same assignments. `sshCommand` resolves git's ssh command in git's own order and appends OpenSSH's batch options; it leaves another program alone (spec R36's exception). `editor.getEnv` gives `undefined`, not null, for an unset variable (P39 c).
  - A pull's argv has `--no-autostash`, which overrides the user's `rebase.autoStash`/`merge.autoStash` (R34 never stashes; needs git 2.27 without `--rebase`). A queued pull reads `symbolic-ref -q HEAD` when it runs and runs nothing unless the branch it was asked for is still checked out: it integrates into HEAD, not the branch on screen. A push names `refs/heads/<branch>`, so it needs no such check.
  - Publish's prompt opens before anything is queued (the request's epoch is taken before it opens), and its answer must name a listed remote. Every prompt hook fires for every prompt: filter by `prompt_type` (P39 h). The pending answer is the section's own, and the hooks, which name no window, go to the active window's section: a prompt is its window's (INV §11.4). Every stage and unstage argv starts with `--literal-pathspecs`, and group writes always list their paths: a bare `git reset` or `add -A` ends merges and resolves conflicts (INV §9.5).
  - A commit's argv is the exception: `commit -q -m <msg>`, with no `--literal-pathspecs`, no `-a` and no paths. git exports that flag to hooks as `GIT_LITERAL_PATHSPECS=1`, and a hook's own glob pathspec then matches nothing (INV §8 P30).
  - Never kill a write: in 0.5.9 `kill()` is a SIGKILL on both runners, and a killed git leaves `index.lock` behind (INV §8 P16). Writes go through `runWrite`, which waits past `WRITE_TIMEOUT_MS` for git to exit, so `OpQueue` never starts the next write while one still holds the lock. Only reads are killed.
  - A deletion stages with `update-index --remove`, never `add` or `rm --cached`. `add` on a deleted path that is now a directory adds its contents and embeds nested repositories. `rm --cached` drops the entry even when the file has come back since the row was read. A Changes rename's original path is a deletion too. Stage all runs the deletions first (INV §8 P14, P23).
  - Every write's argv is built from the rows on screen, which may be stale by the time it runs, so each command must take its paths' state when it runs. `add`, `update-index --remove` and `reset` do; that is why a key can be released after a failed refresh.
  - A rename's write names its original path too; a copy's names only its new path (R15).
- **Failures.** A definitive failure before anything is shown removes the section (R1). After that, the last good result stays on screen (R10).
- **Epoch and writes.** Diff builds, writes and each group chunk re-check `epoch` after every await. A write that finishes across an epoch change only logs. A status that was running when a write finished is not drawn (`writeSeq`).
- **Selection by key, then by place.** `select`, `expand`, `activate` and `action` record the selection; `context` does not (the host does not move it). When the selected row goes, the selection takes the same offset in the same group, not the old global index (R10, R15).
- **Contexts.** `git-sidebar-rows` is set exactly while the active window's section shows status rows (`rows`), and lists the row commands; `git-sidebar-shown` is set exactly while it is shown at all (`shown`), and lists Focus. Contexts are stored per window and written to the active one (INV §8 P33): `setRows` and `setShown` write them only while their window is active, and `syncContexts` sets both on every switch. Nothing else calls `setContext`; load clears both (R18, R22).
  - Next Change and Previous Change are registered with `DIFF_MODE` as their context: the host lists a command whose context is the focused buffer's mode, so they are listed exactly while a section diff is the active tab, in any window, with no `setContext` (R29, INV §8 P39 k, P42 g). So only the diff's sources may have `DIFF_MODE`; View Commit's buffer has no mode. Their handlers still check that the active buffer is one of the slot's view's sources (`activeDiff`), for a key bound to them.
  - Their moves run on the view's own hunks (`stepHunk` from the focused pane's cursor byte, and from `View.at`, the hunk last moved to: hunks with no lines on a side can share its jump), set both sources' cursors and centre the change in the focused pane; null at either end says R29's message. No host call reports the end.
- **Focus.** Only the Focus command sends `floatingPanelControl(panel, "focus")`, for the active window's section (the host sees no other); no mount, update or refresh does (R1). It shows a hidden explorer column and expands a collapsed section, so the undeclared `"reveal"` is not needed (INV §8 P27). Recheck that after a Fresh upgrade.
- **Auto-reveal (R23).** It acts only on `active_buffer_changed`; a refresh never moves the selection to the active file (R10). `sectionFocused` comes from the section's panel's `focus`/`blur` and from `chrome_focus_changed`, and a remount resets it: a tab click sends `blur` before the buffer change and the chrome event after it, and a remount sends only the chrome event (INV §8 P28).
- **Panels.** Each window's section has its own panel id (never 0, 1 or 2), and panel 2 is the right-click menu. Route panel 2 before looking up a section by panel. A menu choice is in `widget_key`, not the payload. Panel 2's `cancel` (Esc, a click outside) closes only the menu: it is never the end, which is a section panel's `cancel`. A window switch closes the menu. Load unmounts panel 1, the section of the plugin before R28.
- **The Graph (R30–R33).** Keys: `g:g` the group, `h:<id>` a commit, `hf:<id>:<path>` a commit's file, `more:hf:<id>` its cap row, `more:h` Load more (`lib/graph_keys.ts`); none can collide with a status key. `rowKind` gives `commit`/`commitFile`/`loadMore`, so every `kind === "file"` check stays status-only, and `groupOf` sends Graph keys to `g:g`, so `reconcile` keeps R10 inside the Graph.
  - Commit files are kept out of `EntryMap`: every write path reads it. Graph rows have their own lookup (`GraphRows`, `rows.graph`), which only menus, the palette, View File and the diff read, and which goes with the status rows when `setRows(null)` clears them. `GraphState.rows()` hands out one map until its commits or files change, so nothing may change it. `rowAction` and `buttonLabel` give none for a Graph key.
  - One builder (`treeFor`) draws every status with the Graph part as it stands, so a status change never drops Graph rows and moves the selection.
  - `GraphState` reads the log in the same tick as the status, after it, so the scheduler's 25% covers both. It reads only when its trigger moved (branch, HEAD, upstream, `ab`, the upstream's id from `rev-parse`) or something forced it (the group expanded, Load more, the window active again); nothing while the group is collapsed; nothing on an unborn branch. A failed log keeps the last good Graph and records no trigger; so does a log that is `""` on a born branch (output that is not UTF-8, P17). A Load more during a log read keeps `force` and `loading`, so the next read uses the new page. Every revision-taking Graph read ends its revisions with `--`: a top-level file named `HEAD` (`head` on a case-insensitive filesystem), or as a commit's id, makes git die as ambiguous otherwise. Files are read lazily on expand, and after a log for expanded commits not read yet; `prune` drops what is no longer listed or expanded. Every spawn checks `live` first.
  - Enter on a commit toggles it in the plugin: the host sends only `activate` (INV §8 P39 g). A click on a row with children sends only `expand`, no `select`.
- **The diff view.** Every diff, a status row's or a commit file's, is built from a `DiffTarget` (`statusDiffTarget`, `commitDiffTarget`) by one `buildDiff`, into the one `DiffSlot`. View Commit is a single read-only buffer of its own (`commitTab`), named `*<id7>:show.diff*` so Fresh colours it as a diff (P36 i), replaced by the next View Commit and closed through `dropView`. The latest request wins across both, through the slot's one generation: View Commit takes it with `slot.claim()`, and a diff build (`begin`) or a refused row (`invalidate`) moves it on. Its key hint is said once per view, when the keyboard is in it: a diff opened from a row waits (`hintFor`) until `chrome_focus_changed` or a tab change puts the keyboard in the editor on one of its panes (R20).
  - **A buffer group, not Fresh's composite view.** A composite never draws scrollbar marks, nor anything a plugin sets on its sources (R39, INV §13.2, P41 f, g). So the diff is a group (`createBufferGroup`, layout from `diffLayout`) whose scrollable panes borrow the plugin's hidden, read-only sources, each under a one-row fixed header panel written with `setPanelContent` (INV §13.3, P42 a). Sources are named `*<label>:<path>*`, with no space after the `:`: Fresh picks their grammar from the text after the last `:` (R21, INV §8 P26). They hold the exact texts, final newline included: `compareBuffers` keeps each line's `\n` (H17, P42 i). Each panel inherits `editor.line_wrap`, so wrap is turned off per panel split (H7).
  - **One pane when a side is empty** (R38 "One side"), decided from the texts' lengths before any buffer is made (`paneSides`). Fresh draws no filler rows in a zero-byte buffer, and an anchor for an empty left side scrolls the right pane past its end (P42 b). So a one-pane diff makes one source, and has no `compareBuffers`, decorations, sync group or anchors (P42 l); its hunks are one over the whole side (`onePaneHunks`).
  - **Decorations come from one `compareBuffers`** of the two sources (byte offsets), turned into overlays, fillers, gutter marks, scrollbar marks and sync anchors by `paint`. The sync group's id is plugin-wide (`syncSeq`): split ids repeat across windows (H13). Fresh's plugins (`compare_files.ts`, `audit_mode.ts`) are GPL: implement from INV §13.3's description, never copy them.
  - **Keys.** In a group Fresh gives none of its side-by-side keys (P41 k), so `DIFF_MODE` binds every key of R20: Enter, `n`/`]`, `p`/`[`, `q`/Esc, Tab/BackTab (`focusBufferGroupPanel`; nothing in one pane) and `j`/`k`, which name Fresh's built-in `scroll_down`/`scroll_up` (P42 f). Those are action names, not API: recheck them after a Fresh upgrade. Cursors are the focused panel's (`getPrimaryCursor`, P41 n); Enter maps a left-pane line to the right side's (`facingLine`, R19).
  - **Closing (R14 "no leftovers").** Close a view by closing its sources not yet closed (`View.open`): that closes its group too (H4). Never `closeBufferGroup` (it leaves the borrowed sources open) or `removeScrollSyncGroup` (the sync group goes with its panes, H13). Every source is closed exactly once: a second `closeBuffer` logs an ERROR (H14), which the tests' `afterEach` catches. So a plugin-initiated close (`q`/Esc, a replace, a stale build) takes the view out of the slot first; `buffer_group_closed` (the tab's `×`, Close Tab, or a source closed from outside) closes only sources `getBufferInfo` still finds, because a source whose close closed the group is already gone then and its `buffer_closed` comes after (P42 j); `buffer_closed` of a source of the view shown (a window closing, H4) closes the rest.
- **Placement (R37).** Fresh puts a buffer group, and a new virtual buffer's tab, in the active split, which can be the utility dock, and a plugin cannot ask which split is the dock (INV §13.1, P41 c, l). Never `showBuffer` or create a section tab without `enterTarget` right before it.
  - A diff replacing the one shown focuses one of the old view's panels, so the new group lands in its split (P42 d (ii), l). Anything else goes to the first `splitCandidates` entry that exists: the replaced tab's split (View Commit's `commitSplit`, recorded when it was shown: `BufferInfo.splits` lists only visible tabs, H15), the tracked `lastSplit`, the first pane showing a file, the top-left pane. Check a split exists without focusing it: `focusSplit` on a split that is gone logs a WARN (P42 e), and `listSplits` leaves out a split whose visible tab is a group (H3), so the shown diff's own split counts too (`splitExists`).
  - No `flush` between `enterTarget` and the creation: a frame between announces the target split's own tab (H16, P42 k). `placing` is counted from `enterTarget` until the creation settles, and `onActiveBuffer` neither reveals (R23) nor tracks while it is set.
  - `lastSplit` is `getActiveSplitId()` on `active_buffer_changed` when the active buffer is a file (`isFile`: not `is_virtual`; never a path, since a terminal has one, H12) or a section tab; seeded at mount.
- **Presses on the selected row (INV §8 P21).** A sidebar tree in the plain layout lays a `▌` mark over its selected row, and the mark swallows every press on that row: its click, its button, a right-click. The tree spec sets `cardBorders: true` with `itemHeight: 1`, which draws the same rows without the mark. Keep both, and recheck after a Fresh upgrade: the type file says `cardBorders` acts only above height 1.
- **Resolve Conflict (R25)** runs merge_conflict's `start_merge_conflict` action right after `openFile`, and only when `listPlugins()` lists merge_conflict enabled: a disabled plugin's action logs an ERROR (INV §8 P29). An action name is not an API, so recheck it after a Fresh upgrade.
- **Host quirks.** `readFile` returns `undefined`, not null, for a file that is not UTF-8. Process stdout that is not UTF-8 comes back lossy (U+FFFD) from `runOnTarget` and as `""` with exit 0 from `spawnHostProcess` (INV §8 P17). The QuickJS runtime has no `TextEncoder` and no Node globals; tests run on Node and do not catch that, so the live check does.
- **Windows (R28, INV §11).**
  - Route widget events by `panel_id`, never by their `window_id`, which names the active window. A `cancel` on a section's panel, or `window_closed`, ends that window's section only (`drop`).
  - Git, status messages, prompts, buffers and `floatingPanelControl` act on the active window. So no git starts for a section whose window is not active: check `live(myEpoch)` (the epoch and `isActive()`) before every spawn, and after every await that leads to one; keep a bare epoch check only where a result should still land in a parked section. With `fake.windows` set, the tests' `afterEach` fails any git or docker run outside the active window's folder. A press on a section's panel does nothing once its window is not active, and `openDiff` and `viewFile` start only in the active window.
  - `say` keeps every message for an inactive window, in order (a repeat of the last one only once), and shows them together when it is active again; a message said there before that comes after them. Showing them drops a diff hint still waiting, which would replace them at once.
  - `dropView` closes another window's diff buffers only once that window is active again (`leftovers`): `closeBuffer` on another window's buffer can leave its split dangling, and `getBufferInfo` answers for the active window only. On the way back it closes only those `getBufferInfo` still finds (H14). A window that closes first takes them with it.
  - Writes queue per repository (`queueFor(root)`), shared by every window on it, so two windows on one repository never write at once.
  - `isActive()` reads `editor.activeWindow()` when it runs. An event's window may be stale by the time it is handled.
  - `authority_changed` also comes on a switch between windows with different labels, after the active window has moved. Restart a section only when its own label changed (`checkAuthority`), never on the hook alone.
  - Only `armActive` arms the timer, for the active window's scheduler. The TICK handler marks the timer fired before anything else, or a later `arm` for the same time does nothing.
- **No rejections.** Every handler, command and async entry point goes through `guarded` or `guardedAsync`. Throw nothing synchronously inside an `async` function that is awaited later: QuickJS reports the rejection before the `await` handles it.
