# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Plugins for the [Fresh](https://github.com/sinelaw/fresh) editor. Each top-level directory is one self-contained package. `docs/` holds the investigation and the spec behind each package.

## Commands

Run these from inside a plugin directory. `fresh` must be on `PATH`.

- `npm install`
- `npm run check` runs `tsc` (no emit, tests included), then `node --test tests/*.test.ts`, then `fresh --check-plugin <entry>.ts`. All three must pass. The last step prints the whole bundled plugin, so read its exit code, not its output.
- Run a single test: `node --test --test-name-pattern '<regex>' tests/<file>.test.ts`

Tests run the `.ts` sources directly through Node's type stripping, so `erasableSyntaxOnly` is on. That rules out `enum`, `namespace` and constructor parameter properties. Each test file prints a `MODULE_TYPELESS_PACKAGE_JSON` warning, which is expected: `type` in `package.json` is Fresh's field (`"plugin"`), so it can't be set to `"module"`.

## Package rules

These come from how Fresh installs and loads packages (`docs/investigations/git-sidebar.md` §2, §4):

- Installing from `<repo-url>#<dir>` copies only that directory. Nothing may import from outside it, so vendor any shared helper into each plugin.
- Fresh loads every top-level `.ts`/`.js` file in a package as a separate plugin, and the file's stem becomes the plugin name and its `plugins.<name>` config key. So keep exactly one top-level `.ts` (the entry) and put helpers in `lib/`. The stem must not be a built-in plugin name (`tests/manifest.test.ts` lists them).
- Target Fresh 0.5.9 and use only APIs declared in the package's `types/fresh.d.ts`. That file is generated by Fresh and copied from `~/.config/fresh/types/fresh.d.ts`; don't edit it. APIs that exist only on upstream master are off limits.
- Fresh's package schema owns `dependencies`, so build tools go in `devDependencies` only.
- `fresh --check-plugin` bundles but does not typecheck. `tsc` is the type check.
- An unhandled promise rejection kills the plugin runtime. Every event handler and async entry point must catch and log errors.

A new plugin also needs its own README, a row in the root README table (name, description, install URL) and an entry in the root `plugins.json` (see Registry).

## Registry

The repo is also a Fresh package registry: users add its URL to `packages.sources` and install from **Package: Packages**. Fresh clones the source repo (`--depth 1`, under `plugins/packages/.index/`) and reads `plugins.json` from its root, so:

- `plugins.json` stays at the repo root. Every plugin has an entry, keyed by its `package.json` `name`: an installed package matches its entry by that name, and a mismatch lists the plugin twice.
- An entry mirrors its `package.json` (description, repository, license, keywords, `latest_version` = `version`, `fresh_min_version` = `fresh.min_version`). Each plugin's `tests/manifest.test.ts` enforces that, so it passes only inside this repo.
- Bump `version` and `latest_version` together when installed users should be offered the change: `↑` shows only when `latest_version` is newer than the installed `version`.
- Never force-push or rewrite `main`. Fresh updates its clone with `git pull --ff-only` only, and keeps reading the stale clone when that fails.

## Specs and requirement IDs

- `docs/investigations/<plugin>.md` records findings about Fresh's API and runtime, cited as `INV §n`. Live probes are `P0`, `P1`… in §8.
- `docs/specs/<plugin>.md` holds the requirements `R1`, `R2`…, plus out of scope, constraints, acceptance criteria and decisions.

Code comments and tests cite these IDs, for example `(R10)`, `INV §7` or `P2`. Look a cited ID up before changing the code around it, and keep the citations accurate when behaviour changes.

## Trying a plugin in Fresh

Install it from a local checkout (**Package: Install from URL**, `/path/to/fresh-plugins#<dir>`), then restart Fresh. `editor.debug` output goes to `~/.local/state/fresh/logs/fresh-server-<pid>.log`. INV §4 and §8 describe the dev loop, and the isolated-`HOME` tmux setup the live probes used.
